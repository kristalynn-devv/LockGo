# LockGo — Requirements (สรุปรวมจากเอกสารต้นทาง)

รวมข้อกำหนดจากเอกสารสองฉบับให้อยู่ในที่เดียว ใช้เป็นแหล่งอ้างอิงหลักระหว่างพัฒนา

| รหัส | เอกสารต้นทาง |
|---|---|
| `[A]` | AI Fullstack Engineer — Technical Assessment |
| `[P]` | LockGo PRD v1.0 (Draft) |

**วิธีอ่าน** — ทุกข้อกำกับที่มาไว้ท้ายบรรทัด บรรทัดที่ขึ้นต้นด้วย ✅ คือจุดที่เอกสารต้นทางมีปัญหาและถูกตัดสินแล้ว รหัสท้ายบรรทัด เช่น C-01 ชี้ไปข้อสรุปใน §25 ของไฟล์นี้

---

## 1. ภาพรวมผลิตภัณฑ์

LockGo เป็นแพลตฟอร์ม Smart Locker ที่ให้ผู้ใช้ค้นหาและจองช่องล็อกเกอร์สำหรับฝากสิ่งของล่วงหน้า ตู้ติดตั้งตามคอนโดมิเนียม อาคารสำนักงาน มหาวิทยาลัย และห้างสรรพสินค้า `[P]` §1 · `[A]` §1

ปัญหาที่แก้ — ผู้ใช้ไม่ทราบว่าตู้อยู่ที่ใด ไม่ทราบว่ามีช่องว่างหรือไม่ ไม่ทราบราคาก่อนเดินทางไป และวางแผนล่วงหน้าไม่ได้ `[P]` §2

ระบบเต็มประกอบด้วย Mobile Application สำหรับผู้ใช้ Web Application สำหรับเจ้าหน้าที่ Backend API ฐานข้อมูล และการเชื่อมต่ออุปกรณ์ `[A]` §1

✅ ภาพรวมระบุว่าผู้ใช้ทั่วไปใช้ mobile app แต่งานที่มอบหมายให้ทำ 4 หน้าจอฝั่งผู้ใช้ด้วย web framework → C-06

**ฟีเจอร์ที่ได้รับมอบหมายรอบนี้คือ Find & Reserve Locker เท่านั้น** `[A]` §2

## 2. ผู้ใช้เป้าหมาย

นักศึกษา พนักงานออฟฟิศ นักเดินทาง ผู้พักอาศัยในคอนโด ผู้ซื้อสินค้าออนไลน์ `[P]` §4.1

สถานการณ์ตัวอย่าง — ผู้ใช้ต้องไปสถานีรถไฟฟ้าเวลา 14:00 และต้องการฝากกระเป๋า 4 ชั่วโมง จึงเปิดแอปค้นหาตู้ใกล้สถานี เลือกช่องที่เหมาะสม แล้วจองไว้ล่วงหน้า `[P]` §4.2

## 3. ขอบเขตฟีเจอร์

ค้นหาตู้ · ดูรายการ · ดูรายละเอียด · ตรวจสอบช่องว่าง · เลือกขนาด · เลือกวันและเวลา · คำนวณราคา · จอง · แสดงผลการจอง · ดูรายละเอียดการจอง `[P]` §5

## 4. User Journey

เปิดแอป → ค้นหาตู้ → เลือกสถานที่ → ดูตู้ใกล้เคียง → เลือกตู้ → ดูรายละเอียด → เลือกขนาดช่อง → เลือกวัน เวลา ระยะเวลา → ตรวจสอบราคา → ยืนยันการจอง → จองสำเร็จ → ได้หมายเลขการจอง `[P]` §6

## 17. ฐานข้อมูล `[A]` §7

ต้องมีอย่างน้อย — Locker · Compartment · Reservation · User
เพิ่ม entity อื่นได้ตามความเหมาะสม และ **ต้องอธิบายความสัมพันธ์ระหว่าง entity**

✅ คำว่า Locker ถูกใช้ทั้งในความหมายตู้และความหมายช่อง → T-02
✅ บังคับให้มี entity User และจัดการกรณีไม่มีสิทธิ์ แต่ §18 จัด Authentication เป็นงานเสริม → C-05

### โมเดลผลิตภัณฑ์ — P-01 · P-02

การจองกันช่องไว้ก่อน แสดงเรทกับยอดรวม แล้วต้อง**ชำระ**จึงจะได้รหัสเปิดตู้ · หน้าจ่ายกรอกฟอร์มเลือกพร้อมเพย์ / บัตร / โอน · Nest เรียกฟังก์ชันบน Supabase เขียน `payments` + `paid_at` · ไม่เก็บเลขบัตร ไม่ต่อ Payment Gateway จริง (§20)

สถานะที่ใช้จริงรอบนี้คือ `Reserved` → `Active` (ฝากของ) → `Completed` (รับของ) และ `Expired` / `Cancelled`

เปิดตู้เป็น mock: `access_code` 6 หลักจากหมายเลขจอง **คืนเฉพาะหลัง `paid_at` มีค่า** หน้าบ้านวาด QR (`LOCKGO:{หมายเลข}:{รหัส}`) ให้ตู้สแกนจากจอมือถือแบบตั๋วหนัง ปุ่มฝาก/รับจำลองว่าตู้สแกนแล้ว ไม่ต่อเครื่องสแกน / Bluetooth / ฮาร์ดแวร์จริง

ฝากได้ขณะ `Reserved` ที่จ่ายแล้ว จนกว่าจะเลย `no_show_deadline` รวมก่อน `start_time` เพราะช่องถูกกันแล้ว ผู้ตรวจไม่ต้องรอชั่วโมงเริ่ม  
รับได้ขณะ `Active` รวมหลัง `end_time` เพื่อไม่ให้ของค้างในตู้  
ยกเลิกได้เฉพาะ `Reserved` ที่ยังไม่จ่าย — จ่ายแล้วใช้รหัสได้แล้ว ยกเลิกไม่ได้

การจองผูกกับช่องเจาะจง ไม่ใช่โควตาต่อขนาด เพื่อให้ใช้ exclusion constraint ได้
